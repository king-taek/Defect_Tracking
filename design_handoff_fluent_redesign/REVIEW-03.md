## 질의 응답

### A18 → Q18 [BLOCKER] clamp 루프 포화

- **결정**: **A 채택**(V 포화 후 채도 감소로 이어가기). 264조합 검증까지 완료한 구현을 그대로 씁니다.
- **이유**: 제안 근거가 정확합니다 - 문서화된 다크 accent `#4CC2FF` 자체가 "밝고 채도 낮은" 색이며,
  밝은 쪽으로 밀 때 채도를 함께 낮추는 것이 그 색에 도달하는 유일한 경로입니다.
  B(커스텀 색 차단)는 `setThemeColor` 를 노출한 설계와 모순됩니다.
- **정확한 값** (조용한 실패 금지 - 게이트):
  ```python
  # clamp 는 성공을 보장해야 한다. 실패하면 예외로 드러낸다.
  def _push(c: QColor, dark: bool) -> QColor:
      h, s, v, a = c.getHsv()
      if dark:
          if v < 255:  v = min(255, int(v * 1.06) + 1)
          else:        s = max(0, int(s * 0.90) - 2)      # V 포화 → 채도 하강
      else:
          if v > 24:   v = max(24, int(v * 0.94) - 1)
          else:        s = max(0, int(s * 0.90) - 2)
      return QColor.fromHsv(h, s, v, a)

  for _ in range(64):
      if ratio >= ACCENT_CLAMP_TARGET: break
      fill = _push(fill, dark); on, ratio = best_on(fill)
  else:
      raise ValueError(f"accent clamp 실패: {base!r} (최종 {ratio:.2f})")
  ```
- **타협 가능 여부**: **게이트** - 루프가 미달 상태로 조용히 종료되는 경로 금지.
  **권장** - 밀어내는 계수(1.06 / 0.94 / 0.90).

### A19 → Q19 [택1] clamp 목표값

- **결정**: **B 채택.** `ACCENT_CLAMP_TARGET = 5.4`. 게이트(합격선)는 **5.0 그대로**.
- **이유**: 지적이 맞습니다. 판정 기준과 생성 목표를 같은 값으로 두면, 생성 결과가 항상 경계에
  얹힙니다. 두 값을 분리하는 게 정석입니다 - **테스트는 5.0으로 판정, 생성은 5.4를 겨냥**.
  이러면 A16(상태색 5.7 이상)과 기준이 어긋나지 않고, 커스텀 색도 여유를 갖습니다.
- **정확한 값**:
  ```python
  ACCENT_GATE         = 5.0    # 테스트 합격선 (변경 없음)
  ACCENT_CLAMP_TARGET = 5.4    # 생성 목표 - 여유 0.4
  # 결과: 라이트 #0078D4 → #006BBD (5.47)   [프리셋 표를 쓰면 #0067B8 5.78]
  ```
- **타협 가능 여부**: **권장**(5.4 - 5.2~5.7 범위 내 조정 가능) / **게이트**(목표 > 합격선).

### A20 → Q20 [확인] 표 값과 알고리즘 불일치

- **결정**: **제안 승인.** 표 = 프리셋 상수(우선), 규칙 = 표 밖 임의 색 안전망.
- **이유**: REVIEW-02 의 표는 제가 손으로 고른 값입니다(`#0067B8` = Fluent 이전 세대 표준색,
  `#7B3FE4` = 채도를 유지한 보라). 알고리즘 산출값이 아니라고 명시하지 않은 것은 제 잘못입니다.
  프리셋은 "표준색에 맞춘 손 선택"이 정당하고, 임의 색은 규칙이 받는 게 맞습니다.
- **정확한 값**:
  ```python
  ACCENT_PRESETS = {                      # 표 우선 - clamp 루프를 타지 않음
      "#0078D4": {"light": "#0067B8", "dark": "#4CC2FF"},   # Windows
      "#009FAA": {"light": "#009FAA", "dark": None},        # QFluent (라이트 조정 없음)
      "#8B5CF6": {"light": "#7B3FE4", "dark": None},        # Violet
  }
  # None = 규칙(clamp)에 위임. 표에 없는 색도 규칙으로.
  # 단 표 값도 게이트 5.0 검증은 거친다 (표가 틀렸을 때 드러나도록)
  ```
- **타협 가능 여부**: 권장.

### A21 → Q21 [BLOCKER] 하위 기준 3.0 을 경계선에 적용

- **결정**: **A 채택.** 하위 기준 대상은 **포커스 링·선택 링으로 한정**. 경계선 4쌍은 게이트에서 제외.
  A17 의 경계선 항목을 **철회**합니다.
- **이유**: 측정값(1.13~1.69)이 제 판단 근거를 무너뜨립니다. Fluent 경계선은 대비로 식별을
  만들지 않고 **형태의 윤곽만 암시**하며, 컨트롤 식별은 채움·그림자·레이아웃이 담당합니다.
  3.0을 강제하면 §1.1·§1.2 를 폐기하는 셈이라는 지적이 정확합니다.
- **정확한 값** (제외하는 대가로 붙이는 조건 - 이쪽이 실제 사용성 요건입니다):
  ```
  하위 기준 (≥ 3.0) 대상  ← 확정
    · 포커스 링 × card / layer / win        (라이트 4.08~4.53, 다크 7.06~8.12 - 통과)
    · 히트맵 선택 링 × 램프 최저·최고 채움   (A22 참조)
  게이트·하위 기준 모두 제외
    · ctrlBd / ctrlBdBottom × ctrlBg
    · cardBorder / cardBorderH × layer / card
  대신 다음을 정적·시각 검사로 요구 (게이트)
    · hover 는 경계선만으로 표현하지 않는다 - 반드시 배경 변화를 동반
      (cardHover / ctrlBgH 가 함께 바뀌는지 검사. 현 명세는 이미 그렇게 되어 있음)
    · disabled 는 경계선만으로 표현하지 않는다 - 채움이 바탕 쪽으로 수축
  ```
  strict xfail 4건은 **제거**하고 게이트 대상 목록에서 빼세요(xfail 로 남기면 영구 부채가 됩니다).
- **타협 가능 여부**: **게이트**(hover·disabled 가 경계선 단독 신호가 아님) / 권장(제외 목록).

### A22 → Q22 [확인] 히트맵 선택 링이 최고 밀도에서 소실

- **결정**: **A 채택**(이중선). B는 **수치상 불충분**합니다.
- **이유**: B를 검산하면 램프 상한 0.85 채움과 1.0 선택 링의 대비는 **약 1.7** 입니다 -
  3.0에 못 미치므로 문제가 완화될 뿐 해결되지 않습니다. 이중선은 램프 어느 지점에서도
  한 겹이 반드시 대비를 만들고, 지도 UI의 표준 관용구(halo)입니다.
  `03-screens.md` §3 의 "선택: 2px accentFill 테두리"는 이 결정으로 **대체**합니다.
- **정확한 값**:
  ```
  선택 링 = die 사각 안쪽으로 2px, 두 겹
    바깥 1px : accentFill      (연한 채움 구간에서 대비 담당)
    안쪽 1px : onAccent        (진한 채움 구간에서 대비 담당 - 라이트 #FFFFFF / 다크 #16140F)
  검증 쌍 (하위 기준 3.0)
    바깥 링 × 램프 최저 채움   : 4.02 라이트 / 5.44 다크   통과
    안쪽 링 × 램프 최고 채움   : 5.78 라이트 / 9.17 다크   통과  (= onAccent × accentFill 과 동일 쌍)
  러버밴드(드래그 사각)도 같은 이중선 + Qt.DashLine
  포커스(키보드)와 선택을 구분해야 하면 포커스는 die 밖 1px 오프셋 링
  ```
  램프 상한은 **1.0 유지**(밀도 최고 구간의 표현력을 깎지 않습니다).
- **타협 가능 여부**: **게이트**(최고 밀도 die 에서 선택이 보일 것) / 권장(이중선 구성).

## 추가로 발견한 사항에 대한 회신

**hover·pressed 방향 반전 - 승인합니다.** 정확한 발견입니다.

```
규칙: hover·pressed 는 onAccent 와 같은 방향으로 밀지 않는다.
  onAccent == #FFFFFF   (어두운 채움) → hover·pressed 는 더 어둡게
  onAccent == #16140F   (밝은 채움)   → hover·pressed 는 더 밝게
```
프로토타입의 QFluent 프리셋 hover `#00B7C3`(밝은 쪽)이 그 증거이고, 저는 파생식을
라이트=어둡게로 일괄 고정하는 실수를 했습니다. 반전 구현을 채택하세요.

**게이트 추가**: hover·pressed 상태도 `onAccent` 와의 대비 5.0을 유지해야 합니다.
테스트 쌍에 `onAccent × accentHover`, `onAccent × accentPressed` 를 추가하세요
(현재 프리셋 3종 × 2테마 × 4역할 검증에 이미 포함된 것으로 보입니다 - 확인만).

**`text` 별도 clamp - 승인.** 글자용 accent 는 채움이 아니라 **페이지 면**(`layer`) 대비로
clamp 하는 것이 맞습니다. `accentText` 는 `card`·`layer` 양쪽 5.0을 만족해야 합니다.
